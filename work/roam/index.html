Roam

I designed and built the core of a Unity engine on iPhone that AI could drive: first turning a player's prompts into a complete, playable 3D game, then editing that game prompt by prompt while they played.

Role
Client Lead (Unity/AI engine)
When

Where
Remote, for a US company
Platform
iOS
Stack
Unity, C#, C# reflection, UniTask, Odin, LLMs, vector databases, WebSockets, wave function collapse

The constraint

iOS allows no code generated at runtime, so the AI could never write the game's code. Everything it did had to go through systems built ahead of time, and those systems had to cover whatever a player might ask for.

Achievements, by impact

  • A reflection engine the AI can edit anything throughThe AI ran on a separate service layer and had to control the game the way a developer controls an editor: material colours, shaders, sounds, any variable on any script. Writing a function for each would never end, so I built a reflection engine with a contract for the AI. A player says "make this ball red" and it happens, with no custom "change colour" function. One line of code hands any marked-up object to the AI to fill in, with attributes setting value ranges and intent.
  • Scripts the AI understands without reading codeAn AI can't tell what a variable does without reading the code, which is slow and expensive, or what "high damage" means in numbers. Every modular script had its variables, behaviours and sensible ranges documented in a vector database. "I want the enemies to move fast" finds the right script, the right variables and how far to change them. Costs went down and responses got faster, and smaller, cheaper models could do the job.
  • The codexEverything the player said was sorted into codex books: enemies, objectives, player abilities, theme. Each agent read only the books it needed. When the game was generated, the codex became the input to procedural systems, so games were built fast and accurately instead of by an LLM writing code.
  • Maps the AI can reason aboutMaps came from wave function collapse, with hand-made modules. Each module's regions were described in vector space, so the AI could set the generator's balances and place things with logic like "snipers go on high ground". The same system made platformers, city maps and dungeons.
  • Editing a game in placePlayers could place and manipulate objects (size, position, grid, selection), or select an area and ask the AI to change it: "add trees here", "make these enemies smaller". Every action was a command exposed to a hierarchy of agents working in parallel.
  • Enemies from modular partsEnemies and other assets were assembled from modular behaviour components, so new combinations gave new behaviour without new code.
  • Asset reuse through vector databasesEvery generated 3D model was stored in a vector database, so later games reused earlier assets instead of generating them again: about $1 per generated asset, against nothing for a reused one.
  • Tools to see what the AI was doingOdin editor tools to watch traffic between the game and the AI service, track token use and speed, and mock iOS locally. A debugger with flagged logs, sent over WebSocket so they can be read in a secret window on an iOS build.
