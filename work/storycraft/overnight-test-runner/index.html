Overnight test runner

I start it around 8 pm and it runs unattended until somewhere between 3 and 8 am: testing the game on real iPhones, fixing what fails, working through tickets, and leaving fixes and a review plan for the morning. That's about a day of developer work per night, on a fixed Claude Max plan, with tokens left over for my own week.

The harness

Agents are good for an hour or two before something stalls them. The work that matters is the harness that keeps them going all night without anyone stepping in:

  • Resources. Three Unity editors, each with its own local backend in Docker, use a lot of RAM. Agents follow protocols for it: sharing an environment, switching to staging, and taking turns on rebuilds, with CPU and RAM managed so nothing starves or crashes the machine.
  • Device builds. Builds go to plugged-in iPhones and come back as test results, without anyone touching a cable or a prompt.
  • Branches. Each task gets its own branch; finished work lands on an integration branch with a review plan for the morning.
  • Review passes. Changes are reviewed by agents before they reach a person.
  • Agent roles and handoffs. Each agent has one role: researcher, ticket writer, coordinator, worker, tester or reviewer. Work passes between them with a written handoff, so no agent's context bloats over a long run, and they're still sharp at 5 am.

Tests that look after themselves

  • Test plans written by agents. When commits change the first-time user experience or the core flow, agents update the affected test plans to match, so the tests don't rot as the game changes.
  • Device testing. One command takes a plugged-in iPhone to a test-ready dev build that agents can control.
  • Scripts first, AI on failure. The tests are Python scripts that play through the full first-time experience in the editor or on the device, with no per-step latency and no tokens spent. When a step fails, an agent takes over: it takes screenshots, compares game state and checks git to decide whether the flow changed on purpose or it's a bug. Then it repairs the script for next time, or files a ticket.
  • A harness that improves itself. Problems in the test harness itself are mostly fixed automatically, by an agent that collects feedback from every run.
  • Play-session reports. Every run is recorded step by step into one readable HTML report.

Overnight mode

Overnight, a coordinator runs the test plans, then hands what failed, plus a queue of tickets from Jira or Notion, to agents across the three editors of the multi-editor runner. In the morning there's a report and fixes waiting for review.

The agents run under a contract they can't change:

  • No access to production.
  • No merges into shared branches; everything goes to review.
  • No weakening tests to make them pass.
  • A hard stop at a set time, and every decision logged.

Hooks check that every C# edit compiles and block the error dialogs that would stall an unattended editor.
